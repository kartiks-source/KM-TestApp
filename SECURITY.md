# Security

How Catalys modules keep secrets and access safe. Covers `modules/stock-watch` (the web app on Railway) and `modules/stock-watch-sheets` (the Google Sheet). Rules that apply everywhere: AGENTS.md rules 7 (no secrets in git, ever) and 8 (Shopify is read-only). Decisions: ADR-0001 (Shopify keys in Key Vault, read-only), ADR-0011 (auth model). Operations: `docs/RUNBOOK.md`.

Found a problem? Tell the repo owner directly (not in a public issue or a shared channel), with steps to reproduce.

## Secrets: what, where, how to rotate

| Secret | What it unlocks | Lives in | Rotate |
|---|---|---|---|
| `ADMIN_PASSWORD` | the whole web app: every page, every `/api` route, Clear, the ingest key, exports | Railway variable (service `web`) | Change the variable and apply it (Railway redeploys). Every session is signed out (the cookie key includes a fingerprint of it). In production it must be 12+ characters or the app won't start. Tell the team the new one by a private channel, never in chat history, a doc or a sheet |
| `VIEW_PASSWORD` (optional) | a view-only sign-in: every page, number and CSV; no write (`POST/PUT/PATCH/DELETE /api/*` → 403), no ingest key, no backup export | Railway variable (service `web`) | Change or remove the variable and apply it: every view session is signed out (a fingerprint of it is inside the signed view cookie). Must differ from `ADMIN_PASSWORD`; the app refuses to start with it set but no `ADMIN_PASSWORD` |
| Session key `DATA_DIR/secret` | signing the `sw_session` cookie (with a fingerprint of `ADMIN_PASSWORD`) | the `/data` volume, mode 600; made on first start | Delete the file and restart: a new one is made and everyone is signed out |
| `PERFORMITY_POC_API_KEY` (alias `TOKEN_API_KEY`), with `PERFORMITY_POC_API_URL` (alias `TOKEN_API_URL`) and optional `PERFORMITY_BRAND_ID` | asking Performity's POC API for a fresh read-only Shopify token for the brand(s) our key is allowed (option A, ADR-0014). Sent only as the `X-Api-Key` header, only from our allow-listed outbound IP | Railway variables (service `web`); the URL and brand ID are not secret but live beside the key | Ask Performity for a new key (one-time link), set the variable (Railway redeploys), check the Data page shows a good pull, then ask them to revoke the old one. A wrong key pauses pulls 15 minutes locally, so we never trip Performity's 5-wrong-keys IP block. Delete `PERFORMITY_POC_API_URL` to stop pulling at once |
| Shopify access tokens from Performity | read access to the store for one pull | process memory only, for that pull (asked again before every pull, never written to disk or logs) | Nothing to rotate on our side: revoking our API key stops new ones |
| Shopify client ID + client secret | read access to the store's products, inventory and orders (`read_products`, `read_inventory`, `read_orders`) | Azure Key Vault: `shopify-<store>-client-id` and `shopify-<store>-client-secret` (or one `shopify-<store>` JSON secret). Stop-gap: Railway variables `SHOPIFY_CLIENT_ID`, `SHOPIFY_CLIENT_SECRET` | The brand rotates the secret in its Shopify Dev Dashboard → update the Key Vault secret (or variable) → restart the app (credentials are cached 30 minutes, the 24-hour Shopify token until near expiry). Check the Data page shows a good pull |
| Legacy `SHOPIFY_ACCESS_TOKEN` (`shpat_…`) | same as above | Railway variable | Revoke in Shopify admin (uninstall the custom app or regenerate), set the new one, restart. Prefer moving to client ID + secret |
| Azure service principal: `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET` (+ `AZURE_KEY_VAULT_URL`) | reading Shopify secrets from the vault | Railway variables | Create a new client secret in Azure (Entra ID → App registrations → the app → Certificates & secrets), set the variable, restart, check a pull works, then delete the old secret. Give the principal **Get** on secrets only |
| `ALERT_WEBHOOK_URL` (optional) | posting into the team channel that gets "Shopify pulls failing / working again" (the URL usually carries the channel's token) | Railway variable; https only (other URLs are ignored) | Regenerate the incoming webhook in Slack / Google Chat, set the variable, delete the old webhook |
| `DIGEST_WEBHOOK_URL`, `DIGEST_WEBHOOK_URL_<ROLE>` (optional, e.g. `_CEO`) | posting into the digest channel(s); each digest carries the store name and its ₹ numbers to whoever reads that channel | Railway variables only: the page never sees them (it shows the host) and `PUT /api/digest/settings` refuses a `webhookUrl` (400) | Regenerate the webhook at the provider, set the variable, delete the old webhook. Point each one only at a channel the role's people may read |
| Ingest key | posting stock and order rows to `/ingest/stock` and `/ingest/order` (Shopify Flow) | `store.json` on the `/data` volume (settings), shown masked on the Data page (admin only); also inside every backup and export | Data page → Shopify Flow → **New key**, then update the `X-Ingest-Key` header in both Flows straight away: rows sent with the old key are refused (401) |
| Session cookie `sw_session` | being signed in for 30 days (admin, or view with `.view.` in the value) | the browser; HMAC-signed with the session key above | Changing `ADMIN_PASSWORD` (or `VIEW_PASSWORD` for view sessions) or deleting `DATA_DIR/secret` signs everyone out |
| Google Sheet "Publish to web" CSV links | anyone with the link can read the Stock log / Order log tabs | Data page settings (`store.json`) and the brand's Google account | In the Sheet: File → Share → Publish to web → stop publishing, publish again, paste the new links on the Data page |
| Backups and exports (`/data/backups/*.json`, `GET /api/export/backup.json`) | all sales data **and the ingest key** | the volume; wherever someone saved a download | Treat a leaked export as a leaked ingest key: rotate it. Delete downloads when done; never commit, attach or paste them |

Never put any of these in code, Markdown, logs, commit messages, chat or a Google Sheet. Before every commit, run the secret check in `docs/DEFINITION-OF-DONE.md` on the staged diff and read every hit: a real value (not a variable name or a placeholder) means stop and remove it.

## Auth model (today)

- **One shared admin password** (`ADMIN_PASSWORD`). The sign-in page (`POST /login`) sets an HttpOnly, SameSite=Lax cookie valid 30 days (`Secure` behind HTTPS), signed with the session key in `DATA_DIR/secret` plus a fingerprint of the password. Scripts can use HTTP Basic auth with any user name (the password may contain `:`). Sign-out is `POST /logout` only.
- **The app refuses to start** when `NODE_ENV=production` (set in the Dockerfile) and `ADMIN_PASSWORD` is missing or under 12 characters; when a Shopify key source is set and there is no `ADMIN_PASSWORD`; and when `VIEW_PASSWORD` is set without `ADMIN_PASSWORD` or equals it. Only a local run with no password is open (everyone is admin).
- **Wrong passwords** (SW-008): one limiter for the form and Basic auth. 10 per IP per 15 minutes → 429 without checking; the IP is the last `X-Forwarded-For` hop (added by Railway's proxy), else the socket. Across all IPs, 100 wrong passwords per 15 minutes switch every new attempt to "password still checked, a wrong one gets 429": the cap slows a spread-out guesser without letting a stranger lock the owner out (critic round 1, SEC-1). The per-IP map is swept and capped at 10,000 entries.
- **View-only password** (`VIEW_PASSWORD`, SW-029, LOGIC.md §13): one gate right after sign-in refuses every `POST/PUT/PATCH/DELETE` to `/api/*` with 403 before any route runs, so every write route below is covered, now and later. A view session never gets the ingest key, and `GET /api/export/backup.json` is admin-only. Same wrong-password limiter as admin.
- **Flow ingest** (`/ingest/*`) is not behind the login: it needs the `X-Ingest-Key` header (`?key=` is still accepted but logged as deprecated, at most hourly and without the key). At most 500 rows per request (413). Refused with 409 once Shopify is connected (ADR-0009).
- **Browser hardening** (SW-016): CSP (`script-src 'self'`, `frame-ancestors 'none'`), `nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, HSTS behind HTTPS. A write to `/api/*`, `/login` or `/logout` from another site (`Sec-Fetch-Site`, else `Origin` vs host) gets 403. Bad JSON, a bad address or a bad body gets 400, never 500 (SW-018); CSV exports guard against spreadsheet formulas (SW-017).
- **Open endpoints:** `/health` → `{"ok":true}`, or 503 with one line saying the store can't be read or saved (no secrets). `/status` → freshness and row counts for an uptime monitor; no names, keys or error text.
- **Outbound calls** carry no key of ours except to Performity: alert and digest webhooks are POSTed as JSON (https only; digest also allows `http://localhost`), never follow redirects, time out after 10 s, and alert text has tokens scrubbed. A webhook that fails never breaks a pull.
- **Shopify is read-only in code:** `src/shopify.js` `assertReadOnly()` lets only GraphQL query documents through (no `mutation`, no `subscription`) and the app asks only for read scopes, because a shared key may carry write scopes. No webhooks are registered.
- **The Google Sheet** never talks to Shopify and holds no key: Shopify Flow writes rows into it with the brand's own Google connection.
- Next: named users / Performity SSO (SW-060).

## Endpoints that change or wipe data

All need the admin login except `/ingest/*`; a `VIEW_PASSWORD` session gets 403 on every one. Each wipe of `store.json` is backed up first (`docs/RUNBOOK.md`); `onorder.json` and `decisions.json` are not in the app backups yet (SW-005), only in Railway volume backups. Full request and response shapes: `modules/stock-watch/API.md`.

| Endpoint | Effect | Undo |
|---|---|---|
| `POST /api/clear` | deletes every stock change and order line, every Mark ordered record and every Decide decision (409 while a pull runs) | rows: restore the `…-before-clear.json` backup; Mark ordered and decisions: only from a Railway volume backup |
| `POST /api/demo` | replaces all data with demo data and forgets Decide decisions (409 while Shopify is connected, and while the store holds real data: Clear first; the page asks to confirm) | restore the `…-before-demo.json` backup |
| `POST /api/import?kind=stock\|order` | adds CSV rows (duplicates skipped; 409 with Shopify connected or a pull running). On a demo store the demo rows and demo decisions go first (demo is never backed up: nothing to lose) | restore a backup from before the import |
| `PUT /api/settings` | planning settings, store name, Sheet links; `newIngestKey: true` rotates the ingest key (breaks Flow until updated). Every change is logged with who made it | set the old values again (the change log on the Data page has them); a rotated key can't be brought back |
| `POST /api/onorder` | Mark ordered: saves or removes on-order records (`qty`, `eta`) for up to 500 variants; they move rows out of Order today | post the same IDs with `qty: 0` (or `clear: true`), or remove it in the product drawer |
| `POST /api/decide` | Decide: stores keep / drop / clear for a slow seller and hides it until its sales move > 50% | post the same `id` with `decision: null` |
| `PUT /api/digest/settings` | morning digest hour, roles, pause (webhook URLs are env only: a `webhookUrl` → 400) | set the old values again |
| `POST /api/digest/send` | sends the digest to the webhook(s) now: store numbers leave the app | can't be unsent; every send is logged |
| `POST /api/sync`, `POST /api/shopify/sync` | fetch new rows from the Sheet links / Shopify now (a first Shopify pull on a demo store clears the demo) | — |
| `POST /ingest/stock`, `POST /ingest/order` | add rows (ingest key, no login) | restore a backup; rotate the key if misused |
| `GET /api/export/backup.json` (admin only), `GET /api/export/reorder.csv` | read-only downloads (the backup includes the ingest key) | — |

Still open: SW-051 (read-only guard tokeniser, refuse keys with write scopes), SW-052 (Sheet sync redirects, host allow-list, size cap), SW-053 (non-root on Railway: the image sets `USER node`, but `RAILWAY_RUN_UID=0` runs it as root so it can write the volume; pinned image digest).
